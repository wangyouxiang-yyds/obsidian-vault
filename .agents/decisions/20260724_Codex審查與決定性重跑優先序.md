## 四個盲點

1. **grouped 必須在決定性正本上整組重做，且 headline 不可無前綴寫「顯著」**——目前 vault 內殘留的「tversky vs baseline ΔM2=+0.053 顯著」「Prithvi+UPerNet vs tversky ΔM1=+0.037/ΔM2=+0.039 顯著」等說法，都是修復前存檔預測算出來的；UPerNet 那組的效應量已經接近 P1 變異量測出的 run-to-run SD（≈0.023）量級，不能無前綴直接寫「顯著」，必須註明「legacy single-run，可排序假說、不構成 confirmatory」。
2. **grouped（event-grouped cluster bootstrap）不修洩漏**——Evaluation Contract v1.0 解決的是「355-scene 統計獨立性」問題，不是「有沒有姊妹景洩漏」本身；洩漏依然存在（350/355 test scene 在同 fold train 有姊妹景），grouped 只是让推論單位對齐到 12 個事件群，不代表洩漏被消除。
3. **僅 ~12 事件群，需要 per-event effect + leave-one-event-out（LOGO）**——12 群里 NOAA 兩大群佔 89%，任何 headline 數字都需要同時附上逐群 Δ 與 LOGO range，單看聚合 CI 容易被一兩個大群主導。
4. **Prithvi+UPerNet 的舊優勢同樣受 augmentation bug 污染**——2026-07-14/15 的 Prithvi pilot/confirm 全部跑在修復前的管線上，「Prithvi+UPerNet 顯著優於 Tversky」這個論文主線的核心主張，必須等一個乾淨的 deterministic anchor（決定性 0.3/0.7 Tversky 正本）站穩之後才能進場驗證，不能沿用舊 pilot 數字直接當作論文主線已確認。

## 制度規則建議（codex 提出，尚未正式採納，記於此供使用者裁決）

- **指定單一 checkout 為 vault main 唯一 writer**：目前 Linux 與 Windows 兩個 checkout 各自可能獨立推進 vault 內容（本輪已實測發生一次同名 commit 分歧，見 2026-07-24 merge 記錄），需要指定一個 checkout 作為唯一寫入端，其餘走 pull-only 或提案制。
- **push 前先 fetch**：避免重演本輪的 non-fast-forward 分歧。
- **main 只收 fast-forward**：不允許需要 merge commit 才能整合的 push，逼迫 writer 在 push 前先同步。
- **validity-changing finding 當天寫 stub**：任何會讓既有結論失效的發現（如本輪的訓練不可重現、溯源洩漏），發現當天就在對應筆記寫一則最小 stub 記錄+ 連結，不要等到專篇筆記完稿才回頭補，避免出現本輪「新專篇已存在超過一週、但舊主張仍散落各處未標記」的落差窗口。
