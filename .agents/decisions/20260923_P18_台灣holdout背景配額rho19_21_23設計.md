## 最終決議（摘要 DESIGN.md §3–§9；正本以 repo `analysis/p18_taiwan_rho_grid/DESIGN.md` 為準）

**§3 訓練協定**：Prithvi-300M + DeepLabV3(ASPP)、Tversky α0.3/β0.7、batch16、AMP、AdamW、差異化 LR、augmentation、mean/std 全沿用 P14/P16；`max_optimizer_steps=33,000`（StepBudget 模式，`deeplab_adapter.py:1508`），CosineAnnealingLR T_max=33,000 按 update 推進，共 528,000 optimizer samples；`epochs=300` 僅安全上限、`patience=301` 不早停；三組等效 epoch 分別為 125 / 113 epochs+117 steps / 104 epochs+32 steps（ρ19/21/23），論文報 updates、不報約略 epoch 數；中斷不得 resume 成正式結果，新目錄由 0 重跑；seed 42、launcher 固定 `CUBLAS_WORKSPACE_CONFIG=:4096:8`、`PYTHONHASHSEED=42`；**不修改共用訓練核心**。

**§4 Checkpoint 選取**：主要＝epoch-end source-Val mIoU best，strict `>`、平手取早；預算到達時 epoch 中途 break 後仍會做一次 validation，第 33,000 步必有一次評估；三組選模機會 125/114/105 次（ρ19/21/23），Methods 明列為已知限制；事前指定敏感度＝33,000-step `last.pt`，須另跑獨立台灣重建流程（獨立 prediction manifest、權重 SHA256、P5 聚合結果），best 與 last 兩套結果都要完整報告，不得依結果擇一；穩健性標記＝對 best、last 各自算三個 pairwise 判定（19−23、21−23、19−21）與唯一勝者狀態，任一 pair 判定類別不同即標「checkpoint-rule-sensitive」。

**§5 主端點與事前判定**：主端點＝P5 定義 `recon(gt_aware)` → 同日 tile 空間去重 → 事件內日期等權 → 兩事件等權 event-macro Oil IoU，decision rule＝argmax。任一 pairwise A−B：兩事件 Δ 皆 ≥+0.02 支持 A 較佳、皆 ≤−0.02 反向、其餘不可判定（含方向不一致或同方向但任一事件未達 0.02）。判定層次：19−23、21−23 為主要 reference contrast，19−21 用於區分候選峰區；只有某組同時以門檻勝過另外兩組，才稱「本次 P18 的唯一較佳組」；19、21 都勝 23 但彼此分不出來→結論為「19–21 候選帶優於 23，無法辨識 19 或 21」；光看 event-macro 單點 argmax 不足以選出冠軍；三組都未過門檻只能寫「不可判定」，不能寫成等效或沒有差異。此為實務幅度判準，非顯著性檢定。

**§6 次要報告（全部描述性，不改變主判定）**：逐事件、逐日期、逐景 Oil IoU；pooled 與 scene-macro Oil IoU；Oil P/R/F1、BG IoU、binary mIoU；所有 pairwise Δ；source-Val best mIoU、Oil IoU、best update、完整學習曲線；實際 optimizer samples。P10 的 size 分層（P7 凍結三分位 3200/14147）可作探索性附件，不得升格為尺度因果。P10 數字只作歷史背景，不與 P18 pooling，也不把絕對分數差解釋為地域效應（581 零油 patch、切分、Val 政策、更新量皆不同）。與 P12–P17 僅限「同一 source-Val best 選模原則下的描述性並列」，不構成受控比較。

**§7 曝光比例的可知範圍**：靜態閘＝Train 清單組成的 ρ = 19.0016 / 20.9994 / 23.0019（與目標 |差|<0.05）、巢狀、BG 零油；動態閘＝log 的 total optimizer samples = 528,000，collate-filtered None = 0、skipped-small = 0，否則 INVALID；口徑聲明＝P18 的 ρ 定義與組別標籤以凍結 Train unique list 的像素組成為準，不宣稱已量測 33,000 updates 的精確累積 runtime ρ；`shuffle=True`、無 replacement／自訂 sampler 下各 patch 進入 batch 的機率對稱，但 drop_last（每 epoch 分別丟 11/2/10 張）以及最後一個不完整 epoch，會讓實際累積 ρ 相對靜態 ρ 產生未量測的小幅隨機偏移；動態閘只能證明三組使用相同總 sample 預算、沒有資料讀取損失，不能證明 runtime ρ 精確等於名目值。Methods/Limitations 必寫：「三個 ρ 值是凍結 unique training list 的名目曝光比例；正式 run 未記錄逐 sample ID，因此 33,000 updates 的實際累積像素比例未直接稽核。」

**§8 允許與禁止的措辭**：允許例如「在 P18 凍結協定、seed 42 及固定台灣兩事件測試上，19 相對 23 的兩事件差皆超過 +0.02」「兩事件方向不一致，無法辨識單一較佳比例」。禁止：19 是台灣／全域最佳比例；統計顯著、跨 seed 穩健、可一般化到台灣；只改比例就造成提升；差 < 0.02 表示等效；用三點二次式頂點宣稱最佳 ρ；把 P18 與 P10 的絕對分數差解釋為地域效應；宣稱改善全景誤報（台灣測試沒有純背景 patch）；依台灣結果決定重跑、改 checkpoint 或補 seed。

## 少數意見（Codex）

R1 原偏好共同 264-update validation grid 選模（每 264 updates 驗一次、共 125 次、三組同一 grid），理由是可避免不等選模機會造成 multiple-opportunity confounding。R2 中 Codex 接受 Claude 改採 epoch-end best＋last.pt 敏感度（避免修改共用訓練核心）作為替代，但要求把不等選模機會（125/114/105 次）明列為限制、last.pt 須另跑完整獨立台灣重建。R3 中 Codex 確認此安排「足以揭露 checkpoint 規則是否改變三組判定」，未再堅持共同 update-grid——**已以 last.pt 敏感度分析處理其原始顧慮**。
