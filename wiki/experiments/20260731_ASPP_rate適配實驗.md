# ASPP Atrous Rate 適配實驗（Prithvi 16×16 網格）

## 1. 實驗背景

**定位**：Prithvi 條件下的 decoder hygiene／機制測試，非效能勝出取向。prereg 於 2026-07-29 由 Claude×Codex 協商後凍結 v1.0（`analysis/p3_aspp_rate/preregistration.md`）。prereg 已預先聲明整體 S 幾乎不可能過採用門檻（稀釋算術：只有 large 分層改善 d 時 ΔS≈0.24·d，要 ΔS=0.02 需 large 漲約 8 點）——本實驗從設計階段就是為了檢驗一個機制假說，不是找一個立即可用的效能提升。

假說源頭是 2026-07-15 的 [[20260716_資料溯源洩漏與評估合約v1|Prithvi+DeepLabV3 head 消融]]決策（`.agents/decisions/20260715_prithvi_dlv3_head消融.md`）當時就已預先標註「rate 18 在 16×16 grid 已知幾何退化，仍照論文標準預註冊」——本實驗是把這個當時擱置的疑點正式拿出來檢驗。

## 2. 假設

Prithvi patch=16、input 256 → 16×16 token 網格；3×3 空洞卷積跨度=2r+1，現行 rates (6,12,18)→跨度 13/25/37，**r=12/18 的離中心採樣點落在網格外（補零）→中大尺度分支塌成 1×1**。這被推測為 Prithvi+ASPP 顯著輸 Prithvi+UPerNet（p=9.7e-08，見 [[20260716_資料溯源洩漏與評估合約v1]]）的機制。候選 (2,4,6) 跨度 5/9/13 三條全進 16×16 格。

**唯一變因**＝`aspp_atrous_rates`；其餘逐項凍結：

| 項目 | 凍結值 |

| Head | torchvision DeepLabHead（ASPP+projection+dropout 0.5+classifier） |
| Loss | Tversky α0.3/β0.7 |
| Seed | 42 |
| Epochs / patience | 300 / 25 |
| Batch size | 16 |
| LR | 5e-5（encoder 0.1×，head 1.0×） |
| AMP | 啟用 |
| Split | 3_fold_stratified_v2 |
| Mean/Std | 沿用現行自動計算值 |
| Threshold / eval code | 與 comparator 共用 |

實作面：`main/prithvi_deeplab.py` 原本把 rates **寫死**成常數、config 旋鈕實際無效（是 bug），本次改為預註冊允許集 `{(6,12,18),(2,4,6)}` 並以傳入值建構 head；`main/test_prithvi_aspp_rates.py` 5/5 PASS。

**Comparator 為何要重跑**：既有 dlv3 pilot（pooled 0.4167）是 2026-07-15/16、決定性修復 `ba25391` **之前**的產物，不可辯護；故 comparator＝(6,12,18) 的決定性 3-fold 重跑（`_dlv3_det`）。

## 5. 觀察與結論

**這落在 prereg 三種結局中的第三種「無證據」**，不是當初認為最可能的「機制成立但不採用」。

- **幾何圖沒有錯**——r=12/18 的離中心採樣點確實落在 16×16 網格外、確實在採樣補零。
- **猜錯的是功能後果**：torchvision ASPP 的 **global-pool 分支** ＋ **補零的大 dilation 卷積**，仍然提供了有用的長距 context；把 rates 縮小 = **有效感受野變小** = 大圖分層反而更差。
- **一句話結論：大 receptive field 對大片 diffuse 油膜是有用的，不是壞掉的。**「補零 ⇒ 分支失效」這個直覺不成立。
- 因此 r=12/18 補零不是 Prithvi+ASPP 輸 UPerNet 的原因，真正原因在別處；rate 調校這條槓桿**關閉**，prereg 列為 follow-up 的 (1,3,5) 沒有理由再做。

**副產品（對計畫任務最有價值的一項）**：base_det 是 Prithvi+ASPP 第一次決定性 3-fold＝**0.4399**，取代舊 pre-fix 的 0.4167 成為計畫任務基線的正式數字。另可注意其 grouped S=0.4606 vs canonical Tversky(ResNet) S=0.4512 僅差 +0.009（低於 0.02 採用門檻），與 2026-07-18「prithvi_dlv3 vs tversky 平手、計畫換 backbone 一案關閉」方向一致——但兩個 S 出自 P2/P3 兩支腳本、**未做正式配對 bootstrap，只能當一致性佐證，不可寫成檢定結論**。

**與 [[20260724_Focal_Tversky小圖實驗可行性評估]] 第 3 段 FTL 判定合起來看：loss 與 rate 兩條槓桿皆已枯竭，精進要換地方找**（多層 tap 餵 ASPP／操作點與 TTA／合成資料）。

## 6. 誠實揭露（必寫）

1. **候選 fold3 曾因系統重開機中斷，重跑本身合法，但補救殘骸事後被誤刪**：2026-07-31 05:06 系統重開機，把 detached chain 打斷在候選 fold3 約 epoch 32（此時 baseline 三折＋候選 fold1/2 已完整）。當時**有依 prereg 保留失敗殘骸**，移至 `result-seg/CV_358clean_gt_expand_prithvi300m_dlv3_aspp246/_ABORTED_reboot_20260731/`。補跑使用 `main/experiments_CV_358clean_gt_expand_prithvi300m_dlv3_aspp246_fold3rerun.yaml`（僅改 `start_fold: 3`，seed 45，位元等價），單折 199 分鐘完成（`train_log/p3_aspp_fold3rerun.log` 09:07:39 START → 13:46:17 exit=0），六折到齊——**這是合法的工程故障重跑，prereg「僅允工程故障重跑、保留 failed artifact」當時完全有遵守**。但 2026-08-03 的 result-seg 舊世代清理把 `_ABORTED_reboot_20260731/` 一併清除了（該目錄已不存在，父目錄 mtime=08-03 09:50，與同批清理 `CV_358clean_gt_expand/`、`_tversky/` 舊世代 run 的時間戳完全一致），且 repo 內沒有留下書面記錄。**制度教訓：清理 result-seg 前必須先確認沒有 prereg 要求保留的 artifact；此段 provenance 目前只存在於 Claude auto-memory，不在 repo 內。**
2. prereg 列為「免費」的機制診斷（各 atrous 分支 spatial variance、activation norm、非中心 kernel 梯度 norm）**未執行**，因此「global-pool 分支＋補零大 dilation 卷積仍提供長距 context」是本篇對量化結果的機制解讀，不是直接測量證據；目前只有 metric 層的反向結果支持這個解讀。
